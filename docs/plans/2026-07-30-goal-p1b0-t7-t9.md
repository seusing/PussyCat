## 人工验收 = spec §10.2 真机证据门（有通过/失败语义，不是手感调优）

四门全绿即可合并（代码 DoD），但 **spec 明写：未验真机门时不得宣称「1a 真机闭环」**。以下四条是门，不是建议。

```bash
npm run tauri dev
```

**门 1 · 三条代表命令各跑一遍**

| 命令 | 期望 |
|---|---|
| `trae-cn/setup` | 直接运行，无弹窗 |
| `mercury/reimbursement-plan` | 直接运行，**不应有多余弹窗**——有就是算法第 8/9 步顺序错了 |
| `antigravity/recent-paths` | 弹确认；确认后可运行 |
| `paperreview/review` | 置灰，就地写明原因 |
| legacy 之外任一命令 | 置灰，说明为「未审定」而非报错 |
| 断开 Host 再开 | 整体「未连接」，不是逐条置灰 |

**门 2 · 确认跨进程持久**：确认 `antigravity/recent-paths` → **完全退出应用** → 重开 → 确认仍在，不再弹。

**门 3 · 撤销生效**：撤销该确认 → 再运行 → 回到需确认。

**门 4 · 指纹漂移的隔离性 —— 这条是唯一验证点，务必做**
人为改 `server/policy-metadata.mjs` 里 `antigravity/recent-paths` 的某个 metadata 值（使其 `decisionFingerprint` 变化）→ 重启 Host → 该命令既有确认**失效、要求重新确认**，而 `mercury/reimbursement-plan`、`trae-cn/setup` 的状态**不受影响**。验完还原。

> 为什么必须人工做：DoD 门 9（无关命令的 deny/分类变化不作废其他命令的确认）在代码层**测不了** —— 覆盖表只有一条 deny 规则，且 `matchedDenyRule` 恒为 null（命中 deny 的命令在算法第 1 步就 return）。**这条性质的唯一真实验证就在这里**，跳过它等于它从头到尾没被验过。

**三处手感调优（门之外，通过后再谈）**：① 确认框文案是否说清「授予什么」而非「点确定继续」（按 I-P5，它挡的是误点与陈旧 UI）；② 置灰说明就地还是集中；③ 409 应触发前端自动重拉 `/catalog/effective` 并提示重新确认，而不是把 409 甩给用户。

**若发现需要改判决逻辑，停下来说明**——那是 Host 判决与真实场景有出入，属 spec 问题，不该在前端绕过（I-P1）。
